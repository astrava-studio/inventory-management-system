- What It Does & Uses:
  Controls customer demand and outbound fulfillment with strict stock reservation:
  1. DRAFT    : SO drafted with customer name, fulfilling warehouse, and items.
  2. CONFIRMED: Atomically locks inventory rows, checks available stock (`on_hand - reserved >= requested`), and increments `reserved` stock. Prevents overselling across concurrent buyers.
  3. FULFILLED: Warehouse staff packs and dispatches goods. Atomically decrements both `on_hand` and `reserved` by ordered quantity, and generates immutable `SALES_DISPATCH` ledger movements.
  4. CANCELLED: If a confirmed SO is cancelled, the reserved stock is automatically returned to available inventory.

- Sign-Up:
  * Finding: There is NO public user sign-up endpoint in the entire API (`POST /api/auth/register` does not exist).

  * Default Seeded Accounts:
    1. Admin   : `admin@inventory.local`   / `Password123!` (Role: ADMIN)
    2. Manager : `manager@inventory.local` / `Password123!` (Role: MANAGER)
    3. Staff   : `staff@inventory.local`   / `Password123!` (Role: STAFF)
- Login:
  * Endpoint: `POST /api/auth/login`
  * Flow: Validates email & password using `loginSchema` (Zod). Queries `prisma.user.findUnique({ where: { email } })`. Verifies password against `passwordHash` using `bcrypt.compare`.
  * Token: Issues a JSON Web Token signed with `JWT_SECRET` containing `{ id, email, fullName, role }` and expiry `JWT_EXPIRES_IN` (default 7 days).
- Token Verification:
  * Middleware: `backend/src/middleware/auth.middleware.ts` -> `authenticate`
  * Header: `Authorization: Bearer <token>`
  * Verifies JWT and attaches payload to `req.user`.

4.2 AUTHORIZATION & RBAC (ROLE-BASED ACCESS CONTROL)
--------------------------------------------------------------------------------
Access permissions are enforced on endpoints using the `requireRole(...)` middleware:
- ADMIN only:
  * Create Warehouse Location (`POST /api/locations`)
  * Update Warehouse Location (`PUT /api/locations/:id`)
  * Delete Product (`DELETE /api/products/:id`)
- ADMIN & MANAGER:
  * Create/Update Product (`POST /api/products`, `PUT /api/products/:id`)
  * CSV Import/Export (`POST /api/products/import-csv`, `GET /api/products/export-csv`)
  * Stock Adjustments (`POST /api/inventory/adjustments`)
  * Create/Order/Cancel Purchase Orders (`POST /api/purchase-orders`, `POST /:id/order`, `POST /:id/cancel`)
  * Create/Confirm/Cancel Sales Orders (`POST /api/sales-orders`, `POST /:id/confirm`, `POST /:id/cancel`)
  * Create/Cancel Stock Transfers (`POST /api/transfers`, `POST /:id/cancel`)
- ALL ROLES (ADMIN, MANAGER, STAFF):
  * Receive Purchase Order (`POST /api/purchase-orders/:id/receive`)
  * Fulfill Sales Order (`POST /api/sales-orders/:id/fulfill`)
  * Dispatch & Complete Stock Transfers (`POST /api/transfers/:id/dispatch`, `POST /:id/complete`)
  * Read Dashboard, Products, Inventory, Orders, Transfers, and Audit Ledger.

4.3 DATA ISOLATION AUDIT: SINGLE-TENANT VS MULTI-TENANT
--------------------------------------------------------------------------------
CRITICAL FINDING:
The system is explicitly engineered as a SINGLE-TENANT, MULTI-USER enterprise warehouse system. 
Data is NOT isolated per user. All authenticated users access and operate on the SAME shared enterprise inventory dataset.

Audit by Database Model & API Query:
1. `products` & `GET /api/products`:
   - Isolation: GLOBAL / SHARED.
   - Query: `prisma.product.findMany({ where })`. No `userId` or `tenantId` filter exists. All staff view the same company SKU catalog.
2. `locations` & `GET /api/locations`:
   - Isolation: GLOBAL / SHARED.
   - Query: `prisma.location.findMany()`. All staff view company warehouses.
3. `inventory_levels` & `GET /api/inventory`:
   - Isolation: GLOBAL / SHARED by warehouse facility.
   - Query: `prisma.product.findMany({ include: { inventoryLevels: ... } })`. No `userId` filter.
4. `purchase_orders` & `GET /api/purchase-orders`:
   - Isolation: GLOBAL / SHARED.
   - Finding: `created_by_id` is recorded for audit attribution, but `findMany` returns ALL company purchase orders regardless of which user created them.
5. `sales_orders` & `GET /api/sales-orders`:
   - Isolation: GLOBAL / SHARED.
   - Finding: `created_by_id` is recorded for attribution, but orders are company-wide.
6. `stock_transfers` & `GET /api/transfers`:
   - Isolation: GLOBAL / SHARED.
   - Finding: `created_by_id` is recorded for attribution; all transfers are visible across warehouses.
7. `stock_movements` & `GET /api/ledger`:
   - Isolation: GLOBAL / SHARED.
   - Finding: Complete company-wide audit ledger. Records `performed_by_id` for compliance tracing.
8. `dashboard` & `GET /api/dashboard/kpis`:
   - Isolation: GLOBAL / SHARED.
   - Calculates company-wide inventory valuation and open orders.

Summary of Missing User-Level Isolation:
Every operational table (`products`, `locations`, `inventory_levels`, `purchase_orders`, `sales_orders`, `stock_transfers`, `stock_movements`) lacks a `tenantId` or `organizationId` foreign key. If this application is ever converted into a public multi-tenant B2B SaaS platform where different companies sign up independently, a schema migration adding `tenant_id` to all tables and automatic tenant filtering across all Prisma queries will be required. For its current intended purpose (a company-internal inventory engine), the shared data model is the correct ERP pattern.

5. KNOWN GAPS, HARDCODED VALUES, OR TODOS
================================================================================

1. User Self-Registration & Administration:
   - There is no user registration endpoint (`POST /api/auth/register`) or user management UI to invite, deactivate, or edit user passwords/roles.
   - Adding a new staff member requires running a script or adding them directly to the database.

2. Password Reset / Recovery Flow:
   - There is no forgot password or reset token workflow. If an operator loses their password, it must be updated manually in the database with a newly generated bcrypt hash.

3. Soft-Deletes vs Foreign Key Restraints:
   - `Product` has `isActive: boolean`, and `Location` has `isActive: boolean`. However:
   - `DELETE /api/products/:id` attempts `prisma.product.delete(...)`. Because foreign keys `inventory_levels`, `purchase_order_items`, and `stock_movements` have `onDelete: Restrict`, deleting any product that has ever had an order, balance, or movement will fail with a foreign key restriction error (P2003).
   - Recommended Fix: Convert `DELETE /api/products/:id` into an archive action (`prisma.product.update({ where: { id }, data: { isActive: false } })`).

4. Default Fallback Secret:
   - In `backend/src/controllers/auth.controller.ts` and `backend/src/middleware/auth.middleware.ts`:
     `process.env.JWT_SECRET || 'super-secret-inventory-jwt-key-2026-phase1'`
   - In production on Render, `JWT_SECRET` should always be explicitly defined in environment variables rather than falling back to the hardcoded development string.

5. Currency Symbol & Formatting:
   - Currency display in the UI formats numbers with standard decimal places but does not have a dynamic currency configuration (it alternates between `$` in MetricCards and general numeric valuation). A tenant-wide currency setting (e.g. `INR (₹)`, `USD ($)`, `EUR (€)`) would improve multi-currency clarity.

6. Automated Low-Stock Notifications:
   - The system tracks `reorderPoint` accurately and flags low stock on the Executive Dashboard (`totalAvailable <= reorderPoint`). However, there is no background cron job or email/webhook dispatcher (e.g. via SendGrid, Resend, or Cloudflare Email) to automatically notify managers when a SKU hits its reorder threshold.

7. Inactive Earlier Prototype Scaffolds:
   - The repository root contains older directories:
     * `/apps/client`
     * `/apps/server`
     * `/packages/types`
   - These are from the early project initialization and are no longer part of the build or deployment pipeline. While harmless, they can cause confusion for developers exploring the repo.
